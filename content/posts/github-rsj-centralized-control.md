> **여러 프로젝트가 같은 규칙으로 문서를 만들도록, 규칙을 한 곳에 모아 둔 저장소입니다.**
>
> [🔗 GitHub 저장소](https://github.com/RyuSeoJin/rsj-centralized-control)

### 0. 만들게 된 계기

게임 기획서 작성, 프로그램 개발, 언리얼 엔진 공부, QA 테스트 진행, 앱 기획, 발표 자료 만들기까지.

여러 프로젝트를 AI(Claude Code · Codex)의 도움을 받아 진행하고 있습니다.

프로젝트를 진행하다 보면 "이 부분은 이렇게 쓰자", "이건 하지 말자" 같은 규칙이 계속 생겨납니다.

그런데 한 프로젝트에서 겪은 일을 바탕으로 규칙을 고쳐도, **다른 프로젝트의 저장소에는 예전 규칙이 그대로 남아 있었습니다.**

새 프로젝트를 시작할 때마다 AI에게 같은 설명을 처음부터 다시 해야 했고, 그러다 보니 결과물의 모양도 프로젝트마다 들쭉날쭉했습니다.

그래서 **모든 프로젝트가 따르는 규칙은 이 저장소 한 곳에서만 고치고, 각 작업 저장소는 그 규칙을 받아서 쓰도록** 나누기로 했습니다.

### 1. rsj-centralized-control이란?

여러 작업 저장소가 함께 쓰는 **중앙 규칙 저장소**입니다.

크게 두 부분으로 나뉩니다.

- **기본 규칙** (`core/base/`) : 어떤 프로젝트든 꼭 따르는 규칙입니다. 문서를 만드는 순서, 글 쓰는 원칙, 변경 이력과 남은 일을 남기는 방법, git 규칙, HTML로 내보내는 규칙 등이 들어 있습니다.

- **골라 켜는 모듈** (`core/modules/`) : 필요한 프로젝트에서만 켜서 쓰는 규칙입니다. 언리얼 엔진 문서, 시스템 기획서, QA 테스트 케이스, 앱 기획 슬라이드, 픽셀 아트처럼 작업 종류마다 나뉘어 있습니다.

켜지 않은 모듈은 AI가 읽지 않기 때문에, 프로젝트마다 필요한 규칙만 가볍게 가져갈 수 있습니다.

### 2. 실제로 써 보면

#### <mark>2.1. 규칙을 한 번만 고칩니다</mark>

예를 들어 QA 프로젝트를 하다가 "테스트 케이스 표에는 이런 칸이 꼭 있어야 한다"는 걸 알게 됐다면, 그 규칙은 중앙 저장소의 `tc` 모듈에서 고칩니다.

다른 QA 프로젝트들은 다음에 규칙을 받을 때 바뀐 내용을 그대로 가져갑니다.

#### <mark>2.2. 무엇이 왜 바뀌었는지 남습니다</mark>

규칙을 바꿀 때마다 `center-change-log.md`에 바뀐 내용과 이유, 받아 가는 쪽에서 해야 할 일을 함께 적습니다.

그래서 시간이 지나도 "이 규칙이 왜 생겼지?"를 다시 찾아볼 수 있습니다.

#### <mark>2.3. 사람이 아니라 도구가 막습니다</mark>

중앙 규칙에는 특정 프로젝트의 이름이나 값을 적지 않기로 했습니다.

"문장에서 프로젝트 이름을 지워도 말이 되는가"를 기준으로, 말이 되면 중앙 규칙이고 아니면 프로젝트 규칙입니다.

이 기준은 사람이 기억해서 지키는 게 아니라 검사 도구와 GitHub Actions가 확인합니다. 프로젝트 파일이 중앙 저장소에 섞여 들어오면 합쳐지지 않습니다.

### 3. 사용 방법

#### 3.1. 처음 받기

받을 저장소 맨 위 폴더에 이름표 파일 `workspace.json`을 하나 두고, 받기 도구를 실행합니다.

```bash
python {이 저장소를 받은 위치}/core/base/scripts/sync_core.py --from https://github.com/RyuSeoJin/rsj-centralized-control --repo-root {받을 저장소}
```

그다음 읽기 규칙 파일을 만들고, 제대로 받았는지 검사합니다.

```bash
python core/base/scripts/regen.py
python core/base/scripts/check_rules.py
```

#### 3.2. 필요한 모듈 켜기

```bash
python core/base/scripts/module.py list
```

목록에서 필요한 모듈을 골라 켜면, 그 모듈의 규칙과 서식, 도구가 함께 따라옵니다.

#### 3.3. 규칙이 바뀌면 다시 받기

```bash
python core/base/scripts/sync_core.py --from https://github.com/RyuSeoJin/rsj-centralized-control --check
python core/base/scripts/sync_core.py --from https://github.com/RyuSeoJin/rsj-centralized-control
```

`--check`로 무엇이 바뀌는지 먼저 확인한 뒤 받습니다.

#### ★ 작업 저장소에서 `core/`를 직접 고치지 마세요!

받는 쪽에서 `core/` 안의 파일을 고쳐 두면, 다시 받을 때 도구가 멈춥니다.

고치고 싶은 규칙이 있다면 이 중앙 저장소로 먼저 옮겨서 고쳐야 합니다.

### 4. 정리

처음에는 이 저장소의 규칙을 기준으로 **기획서 정본 하나**를 유지하고, 그 정본에서 시뮬레이터나 QA 테스트 케이스 같은 작업물을 만들려고 했습니다.

하지만 정본을 매번 최신으로 유지하기는 어려웠고, 지금은 기획서를 가벼운 마크다운으로 남기는 쪽으로 방식을 바꿨습니다. 그 이야기는 [markcont 소개글](/github-markcont)에 정리해 두었습니다.

그래도 "프로젝트마다 쌓인 경험을 한 곳에 모아 두고 모두가 받아 쓴다"는 이 저장소의 역할은 그대로입니다.
